# AGENTS.md

## Назначение и область действия

Это общий набор инструкций для агентов в репозитории PHANTOM. Прочитай его один раз,
если содержимое ещё не передано в активных инструкциях. Не перечитывай без необходимости.

Задача пользователя определяет результат и границы работы, навыки — порядок выполнения,
а спецификации — инженерные ограничения. Не расширяй узкую задачу до полного аудита или
перепроектирования. При конфликте с нормативным требованием укажи его и не выполняй
действия, безопасность которых не подтверждена.

## Навигация

1. До изменений проверь `git status`, изучи нужный код и существующие тесты.
2. Для текущего раздела используй
   `python tooling docs --document <FILE.md> --locate <section>`, затем прочитай
   ограниченный диапазон. Старый глобальный номер разрешается через
   `--locate <legacy-section>` без `--document`. Не загружай все спецификации.
3. Владельца требования найди в [правилах спецификации](docs/specification-governance.md#sec-specification-governance-2).
   [Системную архитектуру](docs/system-architecture.md) читай при работе с границами
   ответственности Quest, EV3, механики и протокола.
4. Для задачи по этапу прочитай [сквозные условия проверки](docs/implementation-stages.md#sec-10-2),
   нужный этап и [текущий статус](docs/current-status.md).
   [Карта реализации](docs/implementation-map.json) помогает отличить будущий этап от пропуска.
5. Применяй подходящие навыки из единственного каталога `.agents/skills/`; зеркала не создаются.
   Для долгой многокомпонентной задачи веди временный план по
   [phantom-implement](.agents/skills/phantom-implement/SKILL.md). Для небольшой правки план не нужен.

## Обязательные ограничения безопасности

- Quest передаёт намерение и целевые положения, но никогда не передаёт команды PWM/duty.
- EV3 принимает окончательное решение о допуске приводов, локальных ограничениях,
  состояниях и безопасности; EV3 выполняет ввод-вывод приводов.
- `phantom-controller` — штатный единственный владелец команд приводам.
  `phantom-safety` может выполнять документированный программный перехват управления,
  но не является независимым аппаратным каналом безопасности.
- `LOCAL_STOP` имеет приоритет над сетевым управлением.
- `POWER_CUT` — независимый физический путь снятия энергии.
- QR используется для инженерной калибровки, локализации и стартовой привязки.
  В обычном `READY` управление использует энкодеры EV3 и не накапливает программный дрейф.
- Сетевой пакет, ошибка Quest или диагностика не расширяют право записи в моторы
  за пределы действующей `actuator_scope_mask`.
- Release и Diagnostic используют общее ядро управления, состояний и безопасности;
  диагностика не ослабляет условия безопасности.

Подробные требования принадлежат [спецификации безопасности](docs/safety.md)
и спецификациям компонентов.

## Источники и генерируемые данные

Следуй [правилам владения требованиями и разрешения конфликтов](docs/specification-governance.md).
Код, статус и исторический отчёт не переопределяют спецификацию. Неоднозначность,
влияющую на безопасность, разрешай до продолжения опасных действий.

- Wire и EV3-local IPC принадлежат `config/shared/protocol/wire-schema.json`, `config/shared/protocol/semantics.json`
  и `config/shared/protocol/ipc-schema.json`; настройки и схемы принадлежат `config/ev3/`,
  `config/quest/`, `config/shared/` и `config/tooling/`. Общие значения задавай один раз;
  профили содержат только отличия от основы. Не правь вручную файлы `generated/`, размеры, смещения и
  канонические артефакты; не создавай конкурирующих копий.
- При изменении кодеков сохраняй владение схемой и запускай общие эталонные и негативные
  тесты совместимости кодеков. Единственный канонизатор JSON — `protocol/jcs.py` (RFC 8785).
- Поле, описанное как действующее, должно существовать в машинной схеме.
  Исправь источник и производные файлы либо явно обозначь поле как относящееся
  к будущему этапу; правила — [Quest](docs/quest-specification.md#sec-5-19-2)
  и [EV3](docs/ev3-specification.md#sec-7-21-2).
- Локальные оглавления обновляются только через `python tooling generate --target docs`.
  Документация не является входом BUILD, конфигурации или сетевого согласования
  совместимости и не влияет на `build_id`.
- После нормативной правки выполни `python tooling generate --target docs`, затем `python tooling check --target docs`. Для машинных схем также выполни их генераторы
  и проверки. Не оставляй новых изменяемых дубликатов; обнаруженные старые копии
  устрани в границах задачи или сообщи о них.

## Проверки и рабочие данные

- Сначала используй детерминированные программные проверки. Симулятор, имитация,
  просмотр исходников и сборка не подтверждают аппаратный PASS.
- Запускай проверки изменённой области и обязательные условия приёмки.
  PASS относится к точной идентичности проверенного кандидата; при изменении
  протокола, сборки, конфигурации, `CommissioningBundle` или артефакта повтори применимые проверки.
  Для воспроизводимого дефекта по возможности добавь регрессионный тест.
- Если оборудования нет, выполни доступные работы и оставь аппаратную проверку
  `NOT_RUN` с точными дальнейшими действиями. Не заявляй не наблюдавшийся PASS.
- `results/**` — игнорируемые временные отчёты, создаваемые только своим инструментом проверки.
  Не редактируй их вручную. Долговечные отчёты публикуются неизменяемыми внешними
  артефактами с URI/SHA-256 по [плану проверки](docs/test-plan.md).
- Геометрия `mechanical/**` влияет на `RobotGeometry` и `MEASURED` параметры.
  `build/**` очищается через `python tooling clean --target build` с предварительным просмотром;
  не удаляй артефакты пользователя вручную.
- Сохраняй несвязанные пользовательские изменения; не выполняй reset/overwrite.
  Секреты, пароли Wi-Fi, PSK и private keys не должны попадать в исходники,
  документацию, манифесты сборки или обычные журналы.

## Завершение задачи

Требуемое поведение и обоснования храни у владельца спецификации, текущее состояние —
в `docs/current-status.md`, порядок работы — во временном плане. Соблюдай
[правила изменения документации](docs/specification-governance.md#sec-specification-governance-6).
Если код догнал существующее требование, обнови статус, а не текст требования.
Сохраняй точное написание технических идентификаторов.

Перед завершением запусти необходимые проверки, просмотри `git diff` и `git status`,
проверь согласованность сгенерированных файлов и ссылок. Сообщи, что реально проверено,
что осталось `NOT_RUN` и какие действия нужны дальше.

Коммит разрешён только по явному запросу пользователя либо по существовавшему до задачи
и одобренному пользователем плану. Созданный агентом план не разрешает коммит.
Если запрошен один итоговый коммит, сделай его после проверок одним сфокусированным коммитом,
если пользователь не запросил другую историю.
