# AGENTS.md

## Назначение

PHANTOM — проект телемеханического управления с повышенными требованиями к безопасности:
Meta Quest 3 отслеживает намерение пользователя, LEGO Mindstorms EV3 выполняет управление
приводами, а физический манипулятор является управляемой системой.

Этот файл — карта навигации и постоянные ограничения для агента, а не полная спецификация.
Он является **canonical** набором правил для любого AI-агента в этом репозитории.

Среда автоматизации может подставлять `AGENTS.md` как проектную инструкцию; любой агент,
которому содержимое не было предоставлено, обязан прочитать файл сам.

Если этот файл уже присутствует в активных инструкциях, не трать отдельный вызов инструмента
на повторное чтение. Если ты не видишь его содержимого — прочитай его один раз перед работой:
без него ты не знаешь инвариантов проекта.

## Навигация по контексту

1. Начинай с задачи пользователя и исследуй минимально необходимую область кода и тестов.
2. Если известна ссылка вида `§x.y`, выполни
   `python tools/docindex.py --locate <section>`, затем прочитай ограниченный диапазон вокруг
   найденного раздела. Не загружай все документы PHANTOM.
3. Читай `docs/PHANTOM/README.md` только если непонятно, какой документ является основным
   владельцем требования или где оно расположено.
4. Читай `ARCHITECTURE.md`, если задача затрагивает границы ответственности между
   Quest/EV3/механикой/протоколом или меняет эти границы.
5. Для задачи по этапу прочитай §10.2 и только нужный раздел в
   `docs/PHANTOM/IMPLEMENTATION_STAGES.md`, затем
   `docs/PHANTOM/status/CURRENT_STATUS.md`.
6. Используй репозиторный Skill, если его описание соответствует задаче. Единственный
   canonical каталог Skills — `.agents/skills/`; agent-specific зеркала не создаются.

## Область задачи и взаимодействие инструкций

Явная задача пользователя задаёт требуемый результат и область работы. Skills задают
повторяемый рабочий процесс, а документы проекта — инженерные ограничения. Не расширяй
узкую задачу до полного редизайна или аудита проекта только потому, что Skill описывает
более широкий процесс.

Явные инструкции пользователя имеют приоритет над общими указаниями Skill, но не отменяют
молча нормативные требования и требования безопасности PHANTOM. Если запрос конфликтует с
нормативным контрактом, укажи конфликт и действуй fail-closed до его разрешения.

Для длинной многокомпонентной задачи создай или обнови план по
`docs/PHANTOM/exec-plans/TEMPLATE.md`. Для небольшой обратимой правки не создавай план только
ради дополнительного процесса.

## Источники истины

Нормативные уровни и основные владельцы информации определены в
`docs/PHANTOM/SPECIFICATION_GOVERNANCE.md`.

- `protocol/wire_schema.yaml` владеет точными schema-representable значениями и layout
  wire-протокола.
- Объявленные репозиторием config schema/generator sources владеют машинно-читаемой структурой
  конфигурации.
- FR/NFR, инварианты безопасности и системная архитектура ограничивают детальные component
  specifications.
- Quest/EV3/mechanical/protocol specifications уточняют эти ограничения в своих областях.
- `TEST_PLAN.md` владеет требованиями к проверкам и evidence.
- Локальный игнорируемый Git каталог `results/**` хранит временные machine-readable
  test/build/device reports. Долговечное evidence публикуется неизменяемым CI/release
  artifact с URI и SHA-256; `status/**` только суммирует опубликованные records.
- `IMPLEMENTATION_STAGES.md` владеет нормативными определениями этапов и их gates.
- `docs/PHANTOM/implementation-map.json` — ненормативная машиночитаемая карта
  `требование → этап → статус → verification`. Она не дублирует текст требования и служит
  только для того, чтобы отличать «намеренно будущий этап» от «забыто».
- Task execution plans владеют только локальным порядком работ и progress.
- Status/ADR/risk records дают контекст и provenance, но не переопределяют нормативные
  контракты.
- Код является реализацией, а не разрешением молча изменить требование.

Если источники противоречат друг другу, не выбирай удобный вариант. Найди и исправь
владельца контракта. Неоднозначность, влияющая на безопасность, трактуется fail-closed.

Частный случай, который встречается чаще всего: **поле присутствует в нормативной prose, но
отсутствует в machine-readable schema**. Это всегда дефект, а не разрешение молча
реализовать поле. Разреши его одним из двух способов и никогда не оставляй расхождение:

1. поле действительно нужно сейчас → добавь его в schema/source, отрази в generated
   артефактах и в тестах, и только потом описывай в prose как действующее;
2. поле относится к будущему этапу → явно помечай его в prose как поле будущего этапа
   (см. §5.19.2, §7.21.2) и не описывай так, будто runtime его уже читает.

`tools/configgen.py` дополнительно проверяет обратное направление: `MEASURED`-поле, названное
в prose, обязано существовать в canonical config и быть зарегистрированным.

## Неизменяемые инварианты PHANTOM

- Quest передаёт intent/targets, но никогда не передаёт raw PWM/duty.
- EV3 является authoritative для допуска приводов, локальных ограничений, state/safety gates
  и motor I/O.
- `phantom-controller` — штатный единственный владелец motor commands;
  `phantom-safety` может выполнять документированный software takeover, но не является
  независимым аппаратным safety channel.
- `LOCAL_STOP` имеет приоритет над сетевым управлением.
- `POWER_CUT` — независимый физический путь снятия энергии, требуемый спецификацией.
- QR используется для инженерной калибровки/локализации и startup reference; в обычном
  `READY` управление использует encoder feedback EV3 и не должно накапливать software drift.
- Ни scope, ни сетевой пакет, ни ошибка Quest, ни Diagnostic surface не могут расширить
  motor-write authority за пределы authoritative `actuator_scope_mask`.
- Release и Diagnostic используют один control/state/safety core; диагностика не может
  ослаблять safety predicates.

## Generated и дублируемые данные

- Не редактируй вручную generated protocol constants/size maps/canonical artifacts и не дублируй packet offsets/sizes как competing source. Это относится и к Quest↔EV3 wire (`protocol/wire_schema.yaml`), и к EV3-local IPC (`protocol/ipc_schema.yaml`): обе схемы генерируют C++/Python/C# артефакты и общие golden vectors. Production codecs могут быть hand-written; при их изменении сохраняй schema-first ownership и запускай общие golden/negative cross-codec tests.
- Не вводи в код собственную канонизацию JSON. Единственный канонизатор — `protocol/jcs.py`
  (RFC 8785); он используется и на host, и на brick, потому что Quest и EV3 обязаны
  независимо получать одинаковые bytes.
- Не редактируй вручную `docs/PHANTOM_SPECIFICATION.md` и
  `docs/PHANTOM/SECTION_INDEX.md`.
- После изменения нормативной документации выполни:
  `python tools/specgen.py`, `python tools/specgen.py --check`,
  `python tools/docindex.py`, `python tools/docindex.py --check`,
  `python tools/doclint.py`.
- Не создавай новых изменяемых дубликатов. Если встретился legacy mirror, нормализуй его к
  основному владельцу/ссылке, когда это безопасно входит в область задачи; иначе не меняй его
  скрытно и сообщи о проблеме.

## Дисциплина проверки

- До изменений исследуй существующий код, тесты и `git status`.
- Сначала предпочитай детерминированные unit/property/golden/replay/simulator tests.
- Simulator, mock, source inspection или успешная сборка никогда не считаются hardware
  `PASS`.
- Если нужного оборудования нет, реализуй и проверь всё возможное, физический gate оставь
  `NOT_RUN` и укажи точные дальнейшие действия/evidence.
- Сохраняй несвязанные пользовательские изменения; не делай reset/overwrite.
- Не утверждай, что тест пройден, если он реально не запускался и результат не наблюдался.
- PASS относится к exact candidate identity из evidence. Если изменился
  `specification_sha256`, `protocol_schema_hash`, build/config/bundle identity или проверяемый
  artifact, старый PASS не переносится автоматически: выполни применимый regression gate.
- Для воспроизводимого дефекта по возможности добавляй regression test.

## Области репозитория за пределами production

- `ev3/bench/**`, `scripts/ev3-bench-*`, `tools/ev3_validation/**` — инженерный
  характеризационный harness **вне production и вне safety-периметра**: своя разводка портов,
  прямые motor writes, собственная привилегированная модель. Не переноси его решения,
  маппинг портов или результаты в production-путь и не считай его выводы DEVICE/HIL evidence.
  Правь его только если задача явно про bench.
- `results/**` — локальное/CI workspace для machine-readable evidence и полностью
  игнорируется Git. Никогда не редактируй отчёт вручную, чтобы получить нужный статус;
  отчёт создаётся только своим runner. Требуемое долговечное evidence публикуется вне Git
  без изменения проверенных artifact bytes.
- `mechanical/**` — физическая сборка, BOM и safety inspection. Изменение геометрии здесь
  имеет нормативные последствия для `RobotGeometry` и `MEASURED` параметров.
- `build/**` — локальные артефакты. Политика очистки: `scripts/build-clean.ps1` (dry-run по
  умолчанию); не удаляй артефакты пользователя вручную.

## Дисциплина документации

- Product/system/component specs описывают требуемое поведение, а не текущий прогресс.
- Нормативные определения этапов находятся в `IMPLEMENTATION_STAGES.md`; task plans —
  в `exec-plans/`; текущее состояние — в `status/`; rationale — в `decisions/`; открытые
  риски — в `risks/`.
- Если изменился behavior/contract, обнови основной нормативный owner и соответствующие tests.
- Если код лишь догнал неизменившуюся спецификацию, не переписывай требование ради progress;
  обнови status/evidence.
- Сохраняй canonical spelling технических идентификаторов.
- Secrets, Wi-Fi passwords, PSK и private keys никогда не должны попадать в docs, source,
  build manifests или обычные logs.

## Завершение задачи

Перед завершением coding task:

1. запусти минимальные relevant checks, затем обязательный gate изменённой области;
2. просмотри `git diff` и `git status`;
3. проверь синхронность generated files/docs;
4. обнови status/docs только там, где этого требуют правила ownership;
5. укажи, что реально проверено и что остаётся `NOT_RUN`.

Commit разрешён только если текущая задача пользователя явно его требует либо если это прямо
предусмотрено существовавшим до текущей работы и одобренным пользователем execution plan.
Execution plan, который агент создал сам во время текущей задачи, не даёт разрешения на commit.
Если запрошен один финальный commit, делай его после проверок одним сфокусированным commit,
если пользователь не запросил другую историю.
