# Архитектурное решение PHANTOM

Прочитай затронутые FR/NFR, [системную архитектуру](../../../docs/system-architecture.md)
и применимые [инварианты](../../../docs/safety.md). Зафиксируй конкретную проблему
или выбор; не начинай перепроектирование всей системы из-за локальной ошибки.

1. Укажи владельцев состояния, данных, проверки и физического side effect. Различай
   user intent, authority EV3, наблюдение состояния и независимую физическую защиту.
2. Проследи один нормальный сценарий и затронутые отказы: stale/duplicate command,
   session/boot change, потерю peer, частично выполненную транзакцию, restart/power loss.
   Отметь момент commit/ACK, сохраняемые данные и условия повторного допуска.
3. Сравни разумные варианты по safety/latency/memory, сложности внедрения и проверяемости.
   Рассмотри сохранение текущего решения. Не добавляй broker, service или framework ради
   гипотетического масштаба фиксированной пары Quest↔EV3.
4. Для выбранного варианта покажи contract delta и способ проверки: unit/property/replay,
   integration и отдельное hardware evidence. Budget/MEASURED значения бери у владельца;
   оценку явно отличай от измерения.
5. Отрази устойчивое решение, причину и ограничения в owning spec. При изменении
   ответственности обнови SYSTEM_ARCHITECTURE, при schema/semantics изменении — соответствующий
   machine source. Текущий прогресс относится к status, порядок реализации — к task plan.

Результат: краткое обоснование, изменённые границы/интерфейсы, diagram если она проясняет
взаимодействие, trade-offs и необходимые проверки. Не создавай отдельный ADR-каталог.
Если пользователь поручил реализацию, продолжи её; обсуждение архитектуры не заменяет работу.
Неразрешённый safety conflict опиши явно и сохрани затронутый путь fail-closed.
